Illustrative case studies based on typical project operations. All clients, data, and figures are fictional. No confidential information is included.

Ticketing and Escalation Workflow

Context
A corporate wellness program with 1,000+ users handled support through an omnichannel platform. The Project team and the Product-IT team worked separately. (Role: Project Officer Intern)
Problem
Tickets were escalated without clear ownership. Issue history was incomplete, and resolution time was hard to track.
Approach
Mapped the existing flow, defined ticket categories and priority levels, set escalation rules by severity, and assigned an owner for each stage.
Deliverables
  • BPMN process diagram
  • Escalation matrix (L1 / L2 / L3)
  • Ticket status definitions
  • Ticket log template
Outcome (expected)
Clear ownership, complete issue history, and faster, more traceable escalation.
Lessons Learned
A workflow only works if every team agrees on the definitions — starting with what counts as "resolved."

Weekly and Monthly Performance Reporting

Context
A fictional client ("Client A") needed a regular view of program performance.
Problem
Data came from several sources — engagement, tickets, consultations, device connections — and numbers could differ between sources.
Approach
Collected data, cleaned and validated it against a second source, built a Power BI dashboard, and ran a pre-send checklist for risks and discrepancies.
Deliverables
  • Dashboard with dummy data
  • Data validation checklist
  • Weekly internal report template
  • Monthly client report template
Outcome (expected)
Consistent reports and fewer revisions requested by the client.
Lessons Learned
Validate before visualizing — each chart should support a decision, not just display numbers.

SLA, Schedule, and Budget Monitoring

Context
A fictional program had an SLA, a delivery schedule, and a payment schedule linked to program targets.
Problem
Gaps between targets, schedule, and budget were found late, which risked delayed payment.
Approach
Built a tracker for SLA performance, milestones, and targets, with early-warning thresholds and a monthly review with stakeholders.
Deliverables
  • SLA tracker (dummy data)
  • Milestone timeline
  • Risk and issue log
  • Monthly status report
Outcome (expected)
Deviations were caught early, and payment targets stayed on track.
Lessons Learned
Early-warning indicators matter more than end-of-month reports.
Real project

SMK Sejahtera — PKL Information System

Project Lead & Coordinator · Team of 2 · Feb 2026 – Jul 2026 · Jakarta

Context
SMK Sejahtera managed PKL (internship) activities manually, with no central system for logbooks, status tracking, or reporting.
Problem
Four processes ran manually: logbook management, student status monitoring, teacher and student reporting, and internship risk prediction.
Approach
Interviewed school teachers and administrative staff, prioritized features against operational needs, planned delivery in phases using Waterfall, tracked progress in Trello, and validated the system with users through UAT.
Deliverables
  • Business process diagrams (before & after)
  • ERD and activity diagrams
  • Requirement list and project timeline
  • UAT results
  • Live system — smksejahtera.live ↗
Outcome
All four processes were automated. Power BI DAX prediction logic was integrated directly into the website, reaching 100% calculation consistency against the original Power BI model across 5,000 logbook records. The system was deployed for school-wide use.
Lessons Learned
Requirements shifted after the first round of stakeholder interviews — internship risk prediction moved from a "nice to have" to a core requirement. Running interviews before locking the backlog made it possible to absorb that change inside the existing Waterfall timeline without delaying deployment.

Supporting document: covered in my undergraduate thesis (methodology and testing chapters), documenting the development and evaluation of this system in full. Summary available on request. Note: the live system does not display real student data.

Real project

YARSI — Appointment Scheduling System

Project Lead · Sep 2024 – Feb 2025 · Jakarta

Context
Students needed an easier way to schedule appointments with stakeholders at YARSI University.
Problem
Scheduling relied on manual coordination through chat and email threads, which frequently led to double-booked slots and delayed confirmations.
Approach
Applied Scrum with weekly sprint planning, managed tasks on Trello, and built the system's database in MySQL with native PHP.
Deliverables
  • Product backlog and sprint plans
  • Trello board
  • ERD
  • Live system — constappyarsi.site ↗
Outcome
One working web-based appointment scheduling system, deployed to production.
Lessons Learned
Weekly sprint planning surfaced blockers early and made shifting priorities visible to the whole team, which reduced rework compared to a single upfront plan.

From a Project Management standpoint, the product backlog and sprint plan are the artifacts that matter most here — not the implementation code.
